# 自动化流程向导界面设计

## 背景

`AutoSwshRng.Core` 与 `AutoSwshRng.Upstream` 已经完成主要上游能力的无界面抽象。
当前 WinForms App 仍由三个顶层标签页组成：`owoow`、`伊机控` 和 `自动化流程`。
其中 `自动化流程` 仍是占位页，尚未把 RNG 搜索、校准、动作序列和设备状态组织成
一个可执行的用户流程。

本设计只定义首版自动化流程 UI。它不继续复刻 owoow 或 EasyCon 原界面，也不重新
引入远程运行、烧录、固件生成、ESP32 配置或脚本语法帮助。

## 设计目标

- 将自动化主路径设计成向导式工作台：目标配置、Seed 与校准、搜索结果、动作计划、
  执行与监控。
- 默认以 dry-run 预览为主，让用户先看清目标、命中帧、动作序列、预计耗时和风险。
- 真实设备执行作为高级/实验性入口，仅在计划校验通过且设备状态满足条件时可用。
- UI 只负责展示、输入收集、状态呈现和用户确认；业务逻辑留在项目自有 Application
  或 Core 服务中。
- 新 UI 不暴露任何上游类型、EasyCon 设备类型、WinForms 控件到项目自有业务接口。

## 非目标

- 不重做 `owoow` 顶层页和 `伊机控` 兼容页。
- 不实现烧录、清除烧录、固件生成、远程运行、远程停止、ESP32 配置等已排除功能。
- 不把脚本 IDE 作为自动化流程的主入口。
- 不要求首版支持所有高级工具的完整 UI；首版优先承载野外遭遇自动化闭环。

## 推荐布局

采用“单页向导 + 右侧运行摘要 + 底部日志”的 WinForms 布局。

```text
自动化流程
┌──────────────────────────────────────────────────────────────┐
│ 步骤导航                         │ 当前计划摘要              │
│ 1 目标配置                       │ 目标、Seed、候选帧        │
│ 2 Seed 与校准                    │ 预计推进、预计耗时        │
│ 3 搜索结果                       │ 风险与前置条件            │
│ 4 动作计划                       │ 设备与采集状态            │
│ 5 执行与监控                     │ 模式：Dry-run / 实机      │
├──────────────────────────────────┼───────────────────────────┤
│ 当前步骤主区域                   │ 摘要详情与快捷操作        │
│                                  │                           │
│ [配置 / 搜索 / 预览 / 执行控件]  │ [重新校验] [导出计划]     │
│                                  │                           │
├──────────────────────────────────┴───────────────────────────┤
│ 日志、校验、错误提示、取消状态                                │
└──────────────────────────────────────────────────────────────┘
```

左侧步骤导航用于降低复杂度；中间区域展示当前步骤的主要表单或结果；右侧摘要始终保留
当前计划的关键事实，避免用户在多个步骤之间迷路；底部日志用于展示校验、搜索、计划生成、
dry-run 和实机执行的事件流。

## 五个步骤

### 1. 目标配置

输入游戏版本、配置档、遭遇类型、区域、天气、目标宝可梦和筛选条件。筛选条件包含 IV、
异色、证章、气场、身高、特性、性格、性别和稀有 EC 等已有 Core 模型支持的能力。

此步骤应提供“加载默认配置”和“重置筛选”按钮，但不直接调用上游 UI 控件。

### 2. Seed 与校准

输入或读取当前 Seed，并配置影响推进计算的校准项：NPC 数、关菜单、保持方向、飞翔、
区域加载、雨滴计数和天气相关假设。

界面要明确区分“用户输入值”和“计算出的校准结果”。当缺少 Seed 或关键校准项时，后续
搜索按钮不可用，并在摘要区显示缺失项。

### 3. 搜索结果

执行候选帧搜索并展示结果表。默认按自动化友好度排序，优先考虑命中距离、校准风险、
动作序列长度和用户筛选匹配程度。

结果表至少展示：推进数、宝可梦、IV、异色、证章、气场、特性、性格、性别、EC、PID、
身高和预计动作成本。用户选择一行后，右侧摘要立即更新。

### 4. 动作计划

根据选中的目标帧生成动作序列。默认只生成 dry-run 计划，展示每一步按键、等待、循环、
预计耗时和取消点。

计划必须有明确状态：未生成、已生成、校验通过、校验失败、已过期。只要用户回到前面步骤
修改目标、Seed、校准或筛选条件，动作计划就标记为已过期，必须重新生成。

### 5. 执行与监控

默认主按钮为“预览执行计划”，不会控制真实设备。真实执行区域折叠在“高级/实验性实机
执行”中，只有在以下条件同时满足时才可启用：

- 动作计划校验通过。
- 串口设备已连接。
- 若流程需要图像识别，采集源已连接并可截图。
- 用户显式打开实验性执行，并确认风险提示。

执行时提供开始、取消、运行状态、当前步骤、错误、日志和通知反馈。取消必须走 Core
服务的取消令牌或等价机制，不允许 UI 线程阻塞等待。

## 架构边界

新 UI 控件位于 `AutoSwshRng.App`，建议替换现有 `AutomationFlowTabControl`
占位内容。控件只依赖项目自有模型、视图模型或 Application 服务。

建议增加一个项目自有 Application 层，用于承载自动化流程编排：

```text
AutomationFlowTabControl
  -> AutomationFlowViewModel / Presenter
    -> Application 自动化流程服务
      -> Core 接口
        -> Upstream 适配器
```

`AutomationFlowTabControl` 不直接引用 owoow、EasyCon、PKHeX、OpenCV、Avalonia
或上游 UI 类型。`AutoSwshRng.Upstream` 继续作为唯一上游边界。现有 `伊机控`
兼容页可以保留，但不作为新流程的业务逻辑宿主。

## 状态与错误处理

- 每个步骤有独立状态：未开始、可编辑、运行中、完成、失败、已过期。
- 输入校验错误以内联提示和摘要区缺失项呈现。
- 上游异常统一转换成用户可读错误，不显示上游类型名或堆栈。
- 长耗时搜索、生成和执行必须支持取消，并把取消记录到底部日志。
- 真实执行必须先通过 dry-run 计划校验，且不允许隐藏地触发任何烧录、远程或固件行为。

## 测试与验收

- App 结构测试验证 `自动化流程` 页包含步骤导航、摘要区、日志区和 dry-run 主按钮。
- App 结构测试验证已排除功能入口不存在：烧录、固件、远程运行、远程停止、ESP32 配置。
- ViewModel 或 Application 测试覆盖目标配置缺失、Seed 缺失、计划过期、取消和错误转换。
- CLI 或无界面测试继续证明同一流程可在不创建窗口的情况下 dry-run。
- solution 构建和 Core、Upstream、CLI、App 测试全部通过后，才能进入真实执行 UI 的默认可见化。

## 首版完成标准

- `自动化流程` 不再是占位页，而是显示五步向导框架。
- 用户可以在 UI 中看到 dry-run 主路径、计划摘要、设备状态和日志区域。
- 真实执行入口默认折叠，并需要明确启用。
- UI 文案不出现烧录、固件生成、远程运行等已排除能力。
- 业务流程后续可以逐步接入 Application 服务，而不需要重写界面结构。
